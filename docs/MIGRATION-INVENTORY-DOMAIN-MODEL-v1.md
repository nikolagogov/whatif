## 2. Migration inventory / issues to resolve

### P0 — establish one source of truth for world states

`worldStates` is present in all 13 article frontmatters, while structured world states also exist in separate YAML files. These are different representations: frontmatter states are presentation-oriented (`date`, `label`, `items[{label,value}]`); standalone states have stable IDs, `worldId`, `divergenceId`, numeric time, epistemic `status`, typed variables, causal provenance, and evidence.

**Decision:** keep article-frontmatter `worldStates` as legacy/editorial summary for current article display during migration; treat `src/data/world-states/*.yaml` as the canonical structured model for simulation and graph semantics. Do not delete or automatically transform the article summaries until a deliberate mapping and UI replacement exist.

### P0 — normalize entity identity and type vocabulary

The entity registry has inconsistent `type` casing/terminology, including `historical-figure`, `place`, `civilization`, and `country` alongside canonical uppercase values such as `PERSON`, `PLACE`, `STATE`, and `POLITY`. This makes filtering and validation fragile.

**Decision:** define a controlled `EntityType` enum in Domain Model v1. Preserve existing IDs; migrate type values through an explicit mapping. Do not derive IDs from names or rename IDs as part of normalization.

### P0 — separate canonical entities from article-local declarations

Article `entities[]` currently carries `id`, `type`, and `name`; the graph builder merges these with the global registry. This creates two writable descriptions of the same entity.

**Decision:** `entities.yaml` owns canonical entity identity/name/type/aliases. Articles should eventually reference entity IDs. During migration, keep compatibility with existing inline objects and report mismatches against the registry; do not break existing article rendering in one step.

### P1 — clarify the role of relationships

`relationships[]` mixes entity-to-entity relations, article-local structural links, and causal relations such as `causes`. A central registry exists, but the schema allows arbitrary strings for `type` in `content.config.ts`.

**Decision:** validate every relationship type against `relationship-types.yaml`; model structural containment, entity relations, causal links, and transition provenance as distinct relation categories. Keep the existing edge names for backward compatibility in v1.

### P1 — stabilize time representation

Timeline events use free-form date strings, while world states/transitions can use `{label, year, precision}`. Existing content includes exact dates, periods, and relative labels.

**Decision:** retain `dateLabel` as source display text and add/require normalized `year` plus `precision` only when it can be grounded. Do not parse ambiguous historical periods into invented exact dates.

### P1 — clarify generated versus authored data

`content-graph.json` is generated output. It must not become an independently edited source. `entities.yaml`, content frontmatter, world-state YAML, transition YAML, and variable definitions are authored inputs.

**Decision:** document the dependency chain and rebuild graph after authored inputs change. Review whether `build-entity-registry.mjs` writes or transforms the canonical registry before changing its role.

## 3. Domain Model v1

### Core entities

- **Article** — editorial entry, identified by `(sector, articleId)`; owns title, description, image, tags/topics and body.
- **World** — alternate scenario/world identified by stable `worldId`; references the baseline/reference world.
- **Divergence** — point where the alternate scenario departs from the reference outcome; belongs to a world and has type, time label, reference outcome, alternate outcome.
- **TimelineEvent** — dated or ordered event in a world; can be caused by a divergence or prior event and can involve entities.
- **Entity** — canonical person, polity/state, place, institution, group, technology, planet, environment feature, or other domain actor/concept; globally identified in `entities.yaml`.
- **Relationship** — typed, directed relation between supported domain nodes; type is controlled by the relationship registry.
- **WorldState** — snapshot of a world at a particular time; stable ID, world ID, divergence ID, epistemic status, variable values, causes and evidence.
- **WorldTransition** — explicit state-to-state change triggered by a timeline event; records changed variables and before/after values.
- **WorldVariableDefinition** — registry for variable key, domain, value type, units/range and meaning.
- **Claim/Evidence** — a proposition and its supporting source/provenance. Current world-state `evidence` is only a lightweight embedded structure, not yet a fully modeled Claim entity.

### Relationships

- Article `HAS_WORLD` → World
- Article `HAS_DIVERGENCE` → Divergence
- Article `HAS_TIMELINE_EVENT` → TimelineEvent
- Article `MENTIONS_ENTITY` → Entity
- Article `RELATED_ARTICLE` → Article
- Divergence `causes` → TimelineEvent
- TimelineEvent `results_in` → TimelineEvent
- TimelineEvent `involves` → Entity
- WorldState `STATE_OF_WORLD` → World
- WorldState `STATE_OF_DIVERGENCE` → Divergence
- WorldTransition `TRANSITION_FROM_STATE` → WorldState
- WorldTransition `TRANSITION_TO_STATE` → WorldState
- WorldTransition `TRANSITION_TRIGGERED_BY` → TimelineEvent
- Entity-to-entity relations are typed by `relationship-types.yaml`.

### Epistemic status

Keep `CANON`, `DERIVED`, `SIMULATED`, `GENERATED`, and `USER` as distinct provenance/status layers in the model. Current world states/transitions use `SIMULATED`; avoid silently assigning a status where the source does not specify one.

## 4. Target ownership rules

| Data | Canonical source in v1 | Generated/read model |
|---|---|---|
| Article metadata/body | `src/content/**/*.md` | Astro content collections |
| Entity identity/type/aliases | `src/data/entities.yaml` | Content Graph |
| Relationship type definitions | `src/data/relationship-types.yaml` | Graph validation/build |
| Structured world states | `src/data/world-states/*.yaml` | Content Graph / future simulation UI |
| World transitions | `src/data/world-transitions.yaml` | Content Graph / future simulation UI |
| World variable definitions | `src/data/world-variable-definitions.yaml` | Validators / future simulation UI |
| Article display summaries of states | temporarily article `worldStates` frontmatter | Current article UI |
| Content graph | generated `src/data/content-graph.json` | Read-only graph for UI |

## 5. Implementation sequence

1. **Do not perform a bulk content migration yet.** Keep current site behavior stable.
2. Add a versioned domain-model document and controlled entity-type enum/mapping.
3. Extend validation to detect article entity vs registry mismatches and unknown relationship types.
4. Add a report-only migration inventory script that lists each article's metadata, world/divergence IDs, timeline IDs, entity IDs, relationship types, and legacy `worldStates` count.
5. Choose one pilot article (`history/alexander-west.md`) because it already has matching standalone world-state and transition data.
6. Migrate that pilot's state display to canonical structured world states; compare output before migrating other articles.
7. Only then migrate remaining state summaries and remove duplicated frontmatter fields when all consumers have moved.
8. Rebuild graph and run `qa`, `world:validate`, `causality:validate`, and `world:transitions:validate` after each migration stage.

## 6. Explicit non-goals for v1

- No database migration or backend introduction.
- No rewrite of all article frontmatter in one operation.
- No renaming of existing entity/world/divergence/timeline IDs.
- No invented dates, claims, evidence, or epistemic status.
- No new simulation/game feature until the domain ownership and provenance rules are stable.
